Spec · hardware-firmware

Clubins firmware — every feature, behind a flag

Replace the hello-world placeholder with a full ESP32-S3 firmware on esp-hal: a cargo-feature flag framework, a committed config file for runtime tuning, the decibel DSP from the existing design notes, six additional sensor drivers, and both ingest transports (HTTP JSON today, MQTT v2 protobuf as designed). Compile-verified on the exact CI toolchain, delivered as PRs.

Why this spec exists

The Clubins device story is ESP32-S3 sensors → ingest → ClickHouse → dashboard. The firmware link in that chain is a println!("Hello, world!"). The request: build the full firmware now, with every capability implemented and switchable — nothing hard-wired, everything behind a flag — so that deciding on features later is a config edit, never a rewrite.

Current signal

hardware-firmware/src/main.rs is a host hello-world with an empty dependency list and zero implemented sensor types. The only sensor design in the repo — the SPK0641HT4H-1 PDM microphone with A/C-weighted level statistics — exists as prose in implementation_notes/decibel.md, unimplemented. The server, meanwhile, already speaks a concrete ingest contract the firmware does not fulfill.

Desired outcome

A real ESP32-S3 firmware crate that compiles on the pinned CI toolchain: capability flags in Cargo.toml, runtime tunables in a committed config/default.toml, the decibel DSP implemented from its design notes, a curated set of additional sensor drivers each behind its own flag, and both ingest transports — the working HTTP-JSON path and the designed-but-unbuilt MQTT v2 protobuf path.

The curated driver set (PDM mic, PIR, BME280, SHT4x, SCD4x, PMS5003, BH1750) plus flag plumbing covers what Patrick will later want. Supporting evidence: the server contract's measurement types (decibel, pax, weather, status) and the repo's own product copy — "sound levels, occupancy, and environmental conditions." What would overturn it: real hardware that none of these drivers speak to. In that case a new driver is a small, flag-scoped PR — which is exactly what the framework is for.

Server-side work stays out of scope: the firmware emits the new measurement types (co2, pm25, light) following the repo's own one-topic-per-type rule; ingest endpoints, ClickHouse tables, and Postgres sensor_types rows for them are a separate backend change. No physical boards are flashed during this build — verification is compile-level plus host test suites.

Evidence from two read-only research passes plus direct reads of the contract sources. One conflicting finding (the ingest JSON field names) was re-verified directly in the Go source before this spec was written; the table reflects the verified values.

What we build

Shape of the crate

One crate, two personalities. Pure-logic modules — config parsing, the sensor trait and registry, the decibel DSP math, and transport encoders — are no_std-compatible with alloc, so they compile and test on the host, keeping CI fast and the existing just check recipes meaningful. Everything hardware-bound — I2S PDM capture, I2C/UART buses, Wi-Fi, NVS, sleep — lives behind esp32s3 and compiles only for the Xtensa target. main.rs stays thin: init config, bring up sensors and transport, run the loop.

pub trait Sensor { fn metadata(&self) -> &'static SensorMeta; // type name, bus, unit, ingest type fn init(&mut self, bus: &mut Bus) -> Result<(), SensorError>; fn sample(&mut self, bus: &mut Bus) -> Option; } // Built at boot: every compiled driver consults config; disabled = absent. pub struct Registry { sensors: heapless::Vec, MAX_SENSORS>, } impl Registry { pub fn from_config(cfg: &Config, bus: &mut Bus) -> Self; // feature-gated arms }

The flag framework

Capabilities are cargo features — the compile-time half of "a flag in a config file." Every sensor driver, both transports, and each ops concern is its own leaf flag with no hidden coupling; the defaults set matches what the server can receive today. Runtime behavior that shouldn't require a recompile (cadences, thresholds, endpoints, which compiled transport is active) is tuned through config/default.toml with NVS overrides — that's the runtime half. The complete matrix is in the flag table.

[features] default = ["sensor-decibel", "transport-http", "ops-status"] # Sensors — each enables its driver and registry arm sensor-decibel = [] # SPK0641HT4H-1 PDM mic, I2S0 @ 48 kHz sensor-pax = ["driver-gpio"] # occupancy front-end (PIR) sensor-bme280 = ["driver-i2c"] # temperature + humidity + pressure sensor-sht4x = ["driver-i2c"] # temperature + humidity sensor-scd4x = ["driver-i2c"] # CO2 sensor-pms5003 = ["driver-uart"] # PM2.5 particulates sensor-bh1750 = ["driver-i2c"] # ambient light # Transports — config selects the active one at runtime transport-http = ["net-wifi"] # working JSON ingest transport-mqtt = ["net-wifi", "proto-v2"] # MQTT v2 protobuf contract transport-mtls = ["transport-mqtt"] # client certs from NVS # Ops ota = [] provisioning = ["net-wifi"] deep-sleep = [] logging-defmt = [] ops-status = []

Decibel, implemented from the design note

The decibel driver is not an interpretation — implementation_notes/decibel.md already specifies the chain: PDM capture at 48 kHz on I2S0, decimation to PCM, DC removal, A- and C-weighting filters, 125 ms Fast windows, LAeq/LCeq with window min/max, overload detection, and a per-unit calibration offset. The calibration offset and overload threshold are NVS-overridable config values. The DSP math (weighting filters, energy accumulation, dB conversion) is pure Rust under dsp/ with host unit tests against synthetic sines at reference levels; only the I2S front-end touches the target.

Transports

HTTP (default, works today): Wi-Fi STA via the esp-rs Wi-Fi stack, then HTTPS POST of one JSON object per measurement to <endpoint>/v1/sensors/<type> with fields exactly as the Go structs define them. The API key is read from NVS, never from the committed config. Failures back off exponentially and drain a bounded offline buffer when connectivity returns.

MQTT (per the v2 design): connect to the broker, publish a retained Status with Online on every connect, then one message per measurement on v2/sensors/<uuid>/data/<type> at QoS 1. boot_id is 16 bytes from the hardware RNG per boot; seq restarts at 0 per topic per boot; a clean disconnect publishes Offline, and the LWT is Died. Protobuf encoding matches the .proto files field-for-field and is conformance-tested against them on the host.

Clock: SNTP after network join; per the contract, timestamps are 0 while unsynchronized so the server can distinguish "no clock" from "wrong clock."

Ops features

Status heartbeats (required by both contracts) are always on. Behind flags: OTA updates via the esp-ota partition scheme, deep-sleep duty cycling that trades measurement continuity for power, BLE-based Wi-Fi provisioning, and defmt logging over UART/USB-JTAG. A hardware watchdog runs unconditionally — it is a safety property, not a feature someone opts out of.

The config file

One canonical config file is committed at hardware-firmware/config/default.toml, compiled into the binary as the defaults. At boot the firmware reads NVS overrides on top — sensor identity, credentials, calibration, and any tuned tunables — so a device is configured without a rebuild, and a fresh flash still boots with sane defaults. Secrets (Wi-Fi credentials, API key, client certificate and key) live only in NVS; the committed file holds placeholders and never secrets.

[sensor] id = "00000000-0000-0000-0000-000000000000" # real UUID lives in NVS [sampling] decibel_window_ms = 1000 # Fast windows are 125 ms inside this report_interval_s = 60 # per-type reporting cadence offline_buffer = 64 # measurements held while disconnected [sensors.bme280] i2c_address = 0x76 [sensors.pir] gpio_pin = 4 [transport] active = "http" # "http" | "mqtt" http_endpoint = "https://ingest.clubins.de/v1/sensors" [transport.mqtt] broker = "mqtt.clubins.de" port = 8883 # TLS listener; plain 1883 only without mTLS [decibel] overload_threshold_db = 120.0 calibration_offset_db = 0.0 # per-unit value from NVS at runtime

Precedence is one rule, tested on the host: NVS value → config/default.toml value → built-in constant. A config edit re-tunes cadences, thresholds, endpoints, and which compiled transport is active; enabling a capability that was not compiled in is the one thing a config edit cannot do — that is the cargo-flag half, and it is deliberate: flags keep the binary small (Wi-Fi and TLS are the big adders on a 128 KB baseline image).

Locked decisions, risks, open questions

  • Target stack: esp-hal 1.2.2 on the pinned 1.97.0.0 fork toolchain; no_std device personality, host-tested pure logic; target builds use rust-lld + -Tlinkall.x + -Zbuild-std=core.
  • Capability flags are cargo features; runtime tunables come from the committed config/default.toml with NVS overrides; secrets exist only in NVS.
  • HTTP-JSON is the default transport (works against today's server); MQTT v2 protobuf is implemented to the api/mqtt contract behind its flags; config selects the active transport at runtime.
  • Single crate this build — no workspace migration (it would break the CI diagnostics remap documented in the firmware README).
  • Decibel is implemented exactly per implementation_notes/decibel.md, including per-unit calibration from NVS.

Risks the plan must carry

  • Signed commits. AGENTS.md requires them; the sandbox has no signing key configured. PR creation is authenticated and will work; if GitHub branch protection rejects unsigned merges, this surfaces at merge time and needs a signing key from Patrick.
  • New ingest types have no server receiver. co2, pm25, light are emitted per the one-topic-per-type rule but land nowhere until the backend grows endpoints/tables. Firmware-side work is complete without it.
  • MQTT is not end-to-end verifiable. The broker is deployed but the ingest bridge does not exist; verification is conformance to the proto files and topic rules, not a live round-trip.
  • PIR hardware is unverified. No PIR is documented in the repo; the pax driver ships behind its flag with a config-chosen pin, honestly reported as motion detections.

None blocking this build. The deliberately deferred product decision — which sensors and transports real deployments want — is answered after this build by editing config and flags, which is the point of the framework. If GitHub rejects merges for unsigned commits, the signing-key setup returns to Patrick.
